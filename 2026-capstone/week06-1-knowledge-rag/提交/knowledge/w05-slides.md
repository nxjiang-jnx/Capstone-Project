## 第 4 页 1.1 长期任务带来的记忆瓶颈

一个修复任务结束后，哪些信息能帮助下一次工作？
上下文不断增长
多轮读文件、测试和修改产生大量历史， 全部重放的输入成本与干扰持续增加。
任务需要跨会话延续
重新开始一个会话后，模型无法自动获得 先前发现的项目约束和失败经验。
信息本身会变化
新的版本和新证据可能推翻旧结论， 只追加记录会让矛盾与过时信息不断累积。
来源：Agent Memory综述v2；Anthropic上下文工程

## 第 7 页 1.2 记忆架构要作出的选择

同一份历史，可以产生不同的系统设计
何时加工历史
写入时先整理，后续读取更直接。 读取时再分析，能适配任务但增加当前开销。
保留哪一种信息
保存摘要，方便恢复“目前做到哪里”。 保存事实，方便沿用项目约束。 保存执行经历，方便理解“试过什么、为什么没有奏效”。 保存形式应服务于未来怎样使用信息。
由谁控制读写
固定策略易预测，模型决策更灵活。 实际系统常把两者组合起来。
来源：Agent Memory综述v2；CoALA

## 第 8 页 1.3 MemGPT：容量瓶颈与分层思路

让有限窗口的模型，能够按需使用窗口之外的信息
问题背景
长期对话和大文档超过窗口。  不断丢弃旧消息， 会损失后续需要的细节。
方法设计
借鉴操作系统的分层存储。  当前窗口保留活跃信息， 外部存储保留更长的历史， 通过函数把信息移回窗口。
外部存储扩大可保存的信息量，真正参与推理的内容仍受窗口限制。
来源：MemGPT

## 第 9 页 1.3 MemGPT：架构与控制流

模型通过函数在当前上下文与外部存储之间移动信息
当前上下文：系统指令、可写工作区、消息队列 外部存储：历史对话与归档信息，需要时再读取
来源：MemGPT

## 第 10 页 1.4 Mem0：冗长对话中的有效事实

直接检索原始对话，往往带回大量与当前问题无关的内容
问题背景
用户事实分散在多次交互中， 可能重复、补充或相互矛盾。  每次从整段对话重新推断， 既消耗输入，也容易遗漏变化。
方法设计
从新交互中抽取候选事实， 再与相关的已有记忆比较。  写入时完成部分整理， 后续按更紧凑的条目检索。
设计重点落在“写入之前怎样整理”，更新机制影响后续回答质量。
来源：Mem0论文；Mem0 开源项目

## 第 11 页 1.4 Mem0：抽取与更新架构

新对话先产生候选事实，再与已有记忆比较
抽取
结合当前对话、 摘要和近期消息
更新
检索相似条目， 决定增、改、删 或保持不变
检索单位从整段对话变成更紧凑的记忆条目。
来源：Mem0论文；Mem0 开源项目

## 第 12 页 1.5 Reflexion：失败反馈的信息量不足

一次“失败”通常没有告诉 Agent 下一次应改变什么
问题背景
Agent 能看到任务失败， 却可能在下一次重试中 重复相同的无效决策。  稀疏反馈难以直接指导修改。
方法设计
结合执行轨迹与评估反馈， 生成可供下一次使用的反思。  把反思保存在经验记忆中， 通过上下文影响后续行动。
Reflexion 在多次尝试间改进决策，原方法不通过梯度更新模型权重。
来源：Reflexion；Reflexion作者代码

## 第 13 页 1.5 Reflexion：经验形成与再利用

后续尝试读取反思文本，模型权重保持不变
Actor：产生行动或程序
Evaluator：依据结果给出反馈
Self-reflection：解释失败并提出修正
反思写入经验记忆， 下一次尝试把它作为上下文。
来源：Reflexion；Reflexion作者代码

## 第 14 页 1.5 Reflexion 的关键限制

加入反思之后，系统仍然需要可靠的反馈和验证。 反馈质量决定经验是否值得保留。
评估可能不充分
自生成测试只覆盖部分输入。 通过这些测试，并不能证明程序完全正确。
解释可能不正确
失败是可观察的结果，失败原因需要推断。 错误归因写入记忆后，会影响后续尝试。
改进需要单独验证
比较相同模型、任务与尝试预算。 区分文本更像反思，和任务结果确实改善。
来源：Reflexion

## 第 16 页 1.7 A-MEM：孤立条目的组织瓶颈

信息逐条保存以后，新的经历可能改变对旧经历的理解
问题背景
独立条目容易丢失信息之间的关联。  新信息到来时，只追加一个条目， 难以更新已有的知识组织。
方法设计
借鉴卡片笔记与关联组织。  先构造带语义信息的笔记， 寻找可能相关的历史笔记， 再建立联系并修订旧笔记。
写入一条新记忆时，系统同时维护它与已有记忆的关系。 维护对象包括记忆内容与关系，组织成本也随之增加。
来源：A-MEM

## 第 25 页 1.11 LoCoMo-Plus：隐含约束是否被使用

新的问题可能与旧线索措辞不同，但回答仍需符合此前目标
论文中的例子
先前：正在准备重要考试，希望减少干扰。 后来：要不要开始追一部热门新剧？
构造上的变化
让旧线索与新问题保持较低语义相似度， 并插入长对话中的时间间隔与无关内容。
评价上的变化
判断回答是否符合历史约束，允许多种合理表达。 不预先提示模型“这是记忆测试”。

## 第 26 页 1.12 从瓶颈选择架构

按记忆条目之间怎样组织来讨论不同方案，分析不同架构的能力与代价
独立条目：轻量追加与检索
组织成本低，便于积累经历。 缺少显式关系，关联推理依赖检索质量。
单层结构：树或图连接记忆

多层结构：跨粒度组织信息

## 第 28 页 2.2 Python Tool：把推理中的步骤交给执行环境

模型生成要执行的程序，运行环境完成计算，再把结果交回给模型。
能力设计
可执行代码承载变量、循环， 组合已有工具与计算库。  执行器返回结果、错误或产物， 模型据此继续任务。

分析批量执行记录。 转换与核对结构化数据。 运行最小验证和测试。  执行能力取决于环境与权限。
语言模型选择计算过程，执行环境负责实际计算与状态变化。

## 第 30 页 2.3 Search Tool：把外部知识引入当前任务

应用场景

## 第 31 页 2.4 工具组合：从材料到验证

一次结论，需要外部文档与本地验证共同支撑
01  先确认项目现状
File 读取锁文件与调用位置， 确定当前版本和受影响的代码。
02  再确认公开变化
Search 找到官方升级说明， 核对需要调整的接口。
03  用执行结果验证
Python 运行最小检查与相关测试， 观察当前环境中的实际行为。
04  给出有范围的结论
说明文档依据、验证条件， 以及还没有检查的部分。

## 第 32 页 3.1 MCP：多服务接入的共同协议

同一个编码应用，可能需要接入许多外部服务
一个代码审查任务
读取仓库中的 Issue， 查内部文档， 再获取持续集成的执行结果。 如果每个应用都分别实现一套接入方式，适配工作会重复。
MCP：Model Context Protocol
服务按共同协议暴露能力， 应用发现并调用这些能力。  模型仍通过工具描述提出动作， 应用控制实际调用。
Function Calling 负责表达调用意图，MCP 支持应用连接外部服务。
来源：MCP规范2026-07-28；MCP架构

连接逻辑在应用中，具体能力由服务提供

## 第 34 页 3.2 服务可以暴露哪些能力

动作、上下文资源和提示模板具有不同用途
能力 | 用途 | 仓库场景中的概念例子
Tools | 可调用的操作 | 查询 Issue、搜索代码
Resources | 可读取的上下文资源 | 项目说明、指定文档内容
Prompts | 可复用且可参数化的提示模板 | 按给定范围组织代码审查任务
实际可用能力取决于 Host 与 Server 的支持，不要求每个服务同时提供三类。

## 第 35 页 3.3 OpenHands 中的 MCP 接入

应用发现服务能力，模型选择动作，服务执行并返回结果
接入后的工作过程
Host 发现服务提供的工具。 把能力描述提供给模型。 把选中的调用交给服务。 把返回结果交回模型。
公开项目例子
OpenHands 可接入 fetch 服务， 读取已知 URL 的内容。  GitHub MCP Server 提供仓库、 Issue 等相关能力。
MCP 统一连接方式，让外部能力进入 Agent 的工具体系， 而如何选择工具、组织上下文和判断任务是否完成，即任务策略与执行控制仍由 Agent 负责。

## 第 39 页 拓展：Memory 与其他相关机制

信息复用、计算复用和参数更新处于不同层面
概念 | 主要操作对象 | 典型用途
显式 Memory | 过去的交互、事实与经验 | 让历史信息影响后续任务
RAG | 检索到的外部材料或记忆 | 为当前生成提供依据
KV Cache | 推理过程中的键和值张量 | 减少重复的注意力计算
微调 | 模型参数 | 通过训练改变模型行为
检索记忆可以采用 RAG 思路；显式记忆的写入通常不改变模型权重。
